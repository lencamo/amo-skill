# Amo Implement

实施并验证已明确的方案，兼顾代码效率、精炼度、可读性和可维护性，规避注释噪音、前端内容污染和范围蔓延。

## 共享输出标记

首行内联前缀使用 `🔨 [amo-implement]`。不要把该标记单独放在一个段落里。

## 使用场景

- 已有明确方案及实施范围。
- 用户要求实施方案并验证结果。

## 不使用场景

- 用户希望设计方案或复核方案。
- 用户希望了解方案详情；使用 `amo-detail`。
- 用户希望审查已实现功能的正确性；使用 `amo-review`。
- 用户希望审查代码风格；使用 `amo-check`。

## 工作流

1. 明确已有方案及实施范围。
2. 查看相关代码、项目约定和已有类型契约。
3. 完成落实方案所需的改动。
4. 检查差异中的方案完成情况、范围和代码质量，修正本次任务引入的问题。
5. 对照方案及其验收条件，对最终实现执行相关验证。
6. 报告实际改动、验证结果及未完成事项。

## 核心规则

### 代码表达

- 遵循项目约定，复用现有模式。
- 满足实际性能需求，消除冗余时兼顾清晰度和可维护性。
- 简单逻辑优先直接表达。为复用、可读性、错误隔离或可测试性的当前收益提取抽象，不仅凭调用次数判断是否必要。
- TypeScript 的局部变量、内部函数和返回值优先依赖类型推断，避免重复注解和手写可可靠推断的复杂返回类型。
- 在公共边界使用显式类型：DTO、组件 props、导出函数参数、请求载荷和响应结构。复用已有契约。
- 优先使用简单类型、现有数据结构和常规类型收窄，避免在清晰度、契约或复用上没有当前收益的类型间接层。
- 使用 composable 时遵循项目约定；无既定约定时，按需解构仅用于展示的 ref/computed 值，修改状态或产生副作用的方法保留在 composable 命名空间下，让来源清楚。

### 注释

- 只解释非显然的原因、约束和行为，不写代码复述、步骤旁白、装饰分隔线、空泛 TODO 或大段实施说明。
- 保留有价值的业务、接口约定及许可证注释；注释清理仅限本次涉及的代码。

### 前端内容

- 页面只呈现需求中的业务内容，不把会话、方案说明、开发过程、技术限制或防错建议擅自做成界面元素；解释留在对话中。
- 方案未要求时，保持现有页面状态和初始值。

### 实施范围

- 只做方案要求及完成它必需的改动，不附带无关功能、清理或重构。
- 不为假设需求增加抽象、依赖、配置或防御分支。
- 排错同样遵守范围；无关问题单独反馈，扩大既定范围前先说明并取得同意。

## 输出

输出标签和内容使用用户的语言。

```text

实施结果：
主要改动：
验证结果：
未完成事项：
```
