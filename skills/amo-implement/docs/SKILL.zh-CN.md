# Amo Implement

实施并验证已明确的方案，兼顾代码效率、精炼度、可读性和可维护性，规避注释噪音、前端内容污染和范围蔓延。

## 共享输出标记

完整交付物的首行内联前缀使用 `🔨 [amo-implement]`。不要把该标记单独放在一个段落里。

## 使用场景

- 已有明确方案及实施范围。
- 用户要求实施方案并验证结果。

## 不使用场景

- 用户希望设计方案或复核方案。
- 用户希望了解方案详情；使用 `amo-detail`。
- 用户希望审查已实现功能的正确性；使用 `amo-review`。
- 用户希望独立审查代码风格。
- 用户希望核实已有审查反馈；使用 `amo-check`。

## 工作流

1. 明确已有方案及实施范围。
2. 查看相关代码、项目约定和已有类型契约。改变共享契约前，识别直接受影响的调用方、测试和数据生产方／消费方，尤其是读取开始抛错、写入中止或提交状态被锁定时。在修复边界内一起处理这些调用方，避免每轮审查再发现一个；不扩展成无关的全仓审计。界面改动在实施前确认真实页面入口、工作区服务、API／数据来源和访问条件，遵循下文运行验收规则。
3. 完成落实方案所需的改动。
4. 检查差异中的需求完成情况、既有行为保留、范围及代码质量，修正本次任务引入的问题。需求核对纳入实施自检，不为它额外安排一轮审查。
5. 按变化的行为和验收条件选择验证。纯展示文字、注释或非执行性文档检查差异、替换覆盖及意外改动，不默认运行业务测试或完整构建；选择器、协议值、插值和可执行指令按行为影响处理。仅涉及展示的布局调整或展示字段移动，检查实际页面及受影响绑定，按需选择编译或类型检查，不默认新增测试或运行全量测试。逻辑改动执行能覆盖变化行为及重要回归的最小必要检查；修改 spec 不代表必须运行该文件全部用例。遵守项目强制检查，冲突时说明而非静默豁免。使用一次性命令，确认范围及选项生效，保留真实退出码和完整失败输出。已有记录中保留测试版本、相关未提交状态、命令、范围、环境、结果及可用日志。中断检查标为未验证；无关失败另行处理，不自动重跑或扩大检查。
6. 报告实际改动、验证结果及未完成事项。本任务启动后台检查或开发服务时，附上运行时句柄、用途，以及是否需要保留供用户验收。
7. 同一实施任务进入首次交付收尾时，读取并使用 `amo-deliver`，即使最初未通过 `amo-workflow` 进入。传递目标、验证证据及缺口、已有审查覆盖与授权，遵守用户指定的范围和操作顺序。

## 核心规则

### 代码表达

- 遵循项目约定，复用现有模式。
- 满足实际性能需求，消除冗余时兼顾清晰度和可维护性。
- 简单逻辑优先直接表达。为复用、可读性、错误隔离或可测试性的当前收益提取抽象，不仅凭调用次数判断是否必要。
- TypeScript 的局部变量、内部函数和返回值优先依赖类型推断，避免重复注解和手写可可靠推断的复杂返回类型。
- 在公共边界使用显式类型：DTO、组件 props、导出函数参数、请求载荷和响应结构。复用已有契约。
- 优先使用简单类型、现有数据结构和常规类型收窄，避免在清晰度、契约或复用上没有当前收益的类型间接层。
- 使用 composable 时遵循项目约定；无既定约定时，按需解构仅用于展示的 ref/computed 值，修改状态或产生副作用的方法保留在 composable 命名空间下，让来源清楚。

### 注释

- 只解释非显然的原因、约束和行为，不写代码复述、步骤旁白、装饰分隔线、空泛 TODO 或大段实施说明。
- 保留有价值的业务、接口约定及许可证注释；注释清理仅限本次涉及的代码。

### 前端内容

- 页面只呈现需求中的业务内容，不把会话、方案说明、开发过程、技术限制或防错建议擅自做成界面元素；解释留在对话中。
- 方案未要求时，保持现有页面状态和初始值。

### 状态行为验证

改动涉及写入或恢复流程时，实施前明确用户应得到的结果，以及失败后必须保留的数据。按实际风险选择下方可达场景；沿用任务记录，保存预期／实际结果和验证方式。

| 触发条件 | 相关场景 | 必须成立的结果 |
| :--- | :--- | :--- |
| 异步保存或上传 | 工作未完成、失败，以及关闭、重开同一对象或切换账号／范围后的迟到成功／失败响应 | 仅归属的操作可消费响应；当前编辑与未保存数据保留。 |
| 本地／云端持久化或恢复 | 客户端与服务端标识不同、部分持久化，以及过期或未完成的恢复进度 | 识别权威记录，保留已完成工作，不重新开放为相冲突的提交。 |
| 已登录写入 | 登录过期、网络失败、重试及旧会话迟到失败 | 失败不能伪装为已确认保存；有意设计的本机／待同步状态保持明确，旧失败不能清除替换后的会话。 |

- 写入或清理依赖已有持久化数据时，须确认该数据读取成功且结构有效；读取或解析失败后的空值兜底不能用于覆盖或删除原数据。
- 在实际更新界面或缓存前校验异步响应归属，包括通过刷新辅助方法间接触发的写入。

界面恢复检查完整操作：显示、启用状态、事件处理、持久化／导航和最终反馈。表单锁定后仍须允许约定的恢复操作，包括恢复字段为空时。

非简单状态逻辑复用充分的已有回归覆盖，或为未覆盖的结果补针对性测试。仅当具体路径存在不可逆数据丢失或越权写入风险，且已有证据不足以确认保护有效时，追加故障注入。修复时，条件允许就证明基线失败、修复后成功；无法执行基线时说明原因。断言用户结果与数据保留，不仅检查内部标记或调用次数。测试总数只总结执行，不代表行为覆盖。

### 运行验收

- 界面改动准备足以判断变化状态的代表性数据。复用已允许使用的数据或约定的本地样例，并说明来源；空页面不能验证有数据时的布局。环境覆盖配置仅保留在当前工作区，生产访问遵守项目授权。
- 从实际渲染的用户入口，以真实鼠标或键盘输入验证变化的界面交互。程序派发事件和组件测试不能证明鼠标命中、事件可达或布局正确。
- 共用界面改动按有实质差异的宿主结构分组，例如遮罩、按钮包装或抽屉，每个受影响组验证一个代表入口。尺寸或选择器匹配变化时，检查实际渲染尺寸或计算样式。
- 实施后提供运行页面，条件具备时检查变化状态。在已有记录或简短报告中保留检查过的入口／动作、预期及实际结果、验证方式，以及未覆盖的宿主组。区分编译／类型检查、浏览器验证和用户验收；数据、登录或运行环境不可用时，说明缺口并提供可用入口，不声称已通过视觉验证。
- 默认完成适用检查后再提交。用户明确要求人工验收前提交时，按其顺序执行，保留待验收状态。

### 实施范围

- 只做方案要求及完成它必需的改动，不附带无关功能、清理或重构。
- 不为假设需求增加抽象、依赖、配置或防御分支。
- 排错同样遵守范围；无关问题单独反馈，扩大既定范围前先说明并取得同意。
