# amo-deliver

## 元数据

- name: `amo-deliver`
- description: 已完成的功能或分支需要最终验收与交付收尾、内部或外部审查意见轮次处理，或交付已审分支时使用。自动推进独立终审与核实后的修复直至收敛。不用于开发中审查、单条意见核实或从需求开始的全程协调。

# Amo Deliver

对完成分支执行收尾闭环：本地体验、独立终审、意见轮次与收敛交付。

## 共享输出标记

每阶段汇报首行行内加 `📦 [amo-deliver]` 前缀，不单独成段。

## 使用场景

- 开发已完成，用户要求收尾、验收或交付该功能。
- amo-workflow 进入最终验收与交付收尾。
- 收尾期间收到审查报告，或用户要求推送、移交已审分支。

## 不使用场景

- 开发中的功能审查；使用 amo-review。
- 不涉及收尾的单条意见核实；使用 amo-check。
- 从需求到验收的全程协调；使用 amo-workflow。

## 仅推送请求

用户仅要求推送已有分支时，确认目标分支、远程／上游和待推送提交。适用验证已完成且没有新变化使其失效时，在授权范围内推送并报告结果，不重新启动体验、审查或验收。缺少验证时如实报告缺口，不宣称已具备交付条件，也不将推送请求视为新增审查／测试轮次的授权。遵守项目强制检查。推送请求不包含提交待处理改动、合并或部署。

## 工作流

1. 明确目标、项目规则、已有授权、验收进度和可用验证。复用有效决策与证据。界面验收时，读取并应用 amo-implement 的“界面验收交接”一节，复用仍有效的已有交接。不给已授权的 commit/push 增加审批前提。仅针对未明确的行为调查后再转 amo-improve 或 amo-fix。
2. 复用仍覆盖目标代码、需求和验收范围的已完成独立审查；否则按下文选择审查路径，首次范围内审查最多安排一名独立审查者。实现者自查不等于独立审查。记录目标的审查状态：已完成并附审查者和覆盖范围、不适用并附豁免依据，或尚未完成并附缺口。阶段切换或产生 commit 本身不要求新开会话。
3. 在协调会话中使用 amo-check 判断返回反馈。核实候选问题和有争议的证据，不重新检查整个差异；本步骤不再启动审查，也不强制另写核实报告。按触发条件、违反的契约与后果去重。按核实后的实际影响判断严重度，不照搬传入标签。保留已确认未满足的需求／验收条件及 Critical/High/Medium 缺陷，非阻塞 Low 建议和误报直接丢弃，不另写驳回附录。未核实的主张保留为缺口。
4. 在已有授权内修复确认的缺陷。明确引入版本与受影响契约，再用 amo-implement 检查直接调用方，完成最小且完整的修复。有帮助时增加针对性回归测试，证明修复前失败、修复后通过。复用不受影响的检查；测试／构建在本验证步骤执行，审查者不重复运行。按下文决定修复复核方式。
5. 必修问题解决且适用证据覆盖目标后交付。结论限定于已审基线／目标及覆盖的流程；区分静态检查、自动化／组件测试、模拟故障、真实接口验证和用户验收。实质缺口或剩余风险交由用户决定；耗时、轮数、测试总数或无发现本身不能证明已可交付。每轮修复完成后主动用一句话报告改动、另一句话报告真实自测结果。提供实际 commit/push 状态与验收需要，不为每个阶段再写完整报告。

## 审查路径

按 amo-review 的行为与后果风险标准选择，不按文件数量：

新增交互触发器，或组件／根节点替换改变了宿主事件或选择器契约时，按行为变化处理，即使补丁主要是 CSS，或已有处理函数未变。

| 改动 | 默认审查 |
| :--- | :--- |
| 展示文字、注释、非执行性文档或范围明确的纯展示变化 | 复用实施自检与适用的页面验证；独立审查记为不适用，用户明确要求或项目规则要求时除外。确认用户输入可达性、事件语义、链接目标、请求、持久化、权限及业务规则未变。 |
| 范围明确的逻辑变化或局部修复 | 一名独立审查者按 amo-review 检查差异及直接受影响契约。即使补丁很小，仍追踪数据丢失等关键失败路径。 |
| 权限、资金、租户隔离、迁移或复杂并发和业务链路 | 独立深入检查相关保护及关联链路。围绕具体风险选择维度，不机械展开所有清单。 |

局部改动优先由一个全新独立会话直接审查。使用宿主已有的委派能力，需要时读取对应运行时指南。默认不让审查者再启动另一个审查进程。复杂工作可选择可用的内置本地 `/code-review` 执行同一套标准，它不是额外必经轮次。遵守用户指定的审查者、工具、模型、力度及项目要求。所需能力不可用时报告缺口，不静默替换或安装工具。使用 Orca 或本地 Claude `/code-review` 前，先读[审查运行时](references/review-runtime.zh-CN.md)。

提供固定基线／目标、需求及有依据的已确认约束、相关项目规则和客观验证证据（版本、命令、范围、结果、可用日志）。提供避免重开未变问题所需的已有裁定，不传交付讨论或预期结论。保留明确选择的提交；包含工作区时，标明已暂存、未暂存及未跟踪输入，并检测审查期间的变化。要求只读报告触发条件、违反的契约、错误结果、影响、源码位置及实质覆盖缺口。未明确分配时，不运行测试、构建、修复或嵌套委派。接受简洁的无发现结论，不强制独立长报告，也不为了改写格式再完整核对一遍。

只维护一份简短记录，保存已审范围／版本、有效验证以及意见的决定、依据和状态。未变覆盖及已定事项直接复用；只有新证据改变触发条件、契约、后果或裁定依据时才重开。历史驳回不能成为忽略新证据证明需求被违反的理由。

## 修复复核

- 检查原触发条件已解决、修复后的用户操作能够完成、直接受影响的调用方保留行为，以及相关回归证据覆盖修复版本。边界明确且没有新风险，代码证据与针对性通过测试覆盖用户结果和数据保留时，可以用本次定向核对收尾；标明它是实施者验证，不冒充新一轮独立审查。
- 修复改变或暴露关键保护、复杂状态转换、现有审查与回归证据未覆盖的实质行为，或用户／项目要求时，安排独立复核。范围固定为修复及受影响契约，只有具体更广影响时才扩大；不逐 commit 或对未变分支范围自动重审。
- 后续轮次发现同根因问题或修复引入的问题时，停止机械追加补丁和审查，重新检查根因、直接调用方与修复边界。在已有授权内继续完成完整修复；仅需求改变、范围扩大或缺权限时提问。不自动拆成新需求，也不把已知阻塞缺陷当成可交付结果。无法补齐前提时，保留现场并报告阻塞。不按固定轮数强制通过。

## 工作现场与运行时

在目标分支已有工作区修复，保留无关改动。尚未检出时，按当前环境的 worktree 规则直接为该分支创建工作区。仅冲突的并行修改或明确隔离要求才增加临时修复工作区，并说明原因。按授权 commit／整合，确认目标包含修复后才宣称交付。仅清理本任务创建且无未提交或未转移工作的临时资源；否则保留并说明位置与原因。

评估工作流耗时时，在已有记录中登记可获得的验证、首轮审查、修复／复核、交接和总耗时，明确所比较的范围。耗时作为效率信号，不是固定质量截止时间。异常拖长时，用运行时支持的方式检查一次进度，判断是否范围扩大、重复工作、调用停滞或意外验证，再针对原因处理。不盲目轮询、重启、提档或扩范围。如实报告未完成覆盖。遵循所选运行时的完成、取消与清理协议，保留无关或用户持有的会话与服务。

## 关键规则

- 优先采用解决已确认问题的最小必要修复，不顺带重构无关代码或扩展功能；检查受影响的既有行为，验证修复没有引入新的回归。
- 核实批评，不为维护实现而拒绝意见；未获用户决定时，不把延期风险视为已接受。
- commit 与 push 授权分离。按项目权限提交确认的修复；推送、合并和对外移交需要明确指令。

## 输出

使用用户的语言和要求的详略程度，先回答当前问题。完整交付物按下方格式输出，保留标签顺序并省略不适用的章节。针对局部追问，只回答该问题和理解答案所需的限定，不重复整份报告，也不重新启动工作流路由。

```text
📦 [amo-deliver] 收尾闭环：<分支>
轮次状态：
修复交付：
收敛情况：
交付状态：
```

整个 amo-deliver 完成后的最后一次回复，在“交付状态”后依次追加“修改说明”“自测结果”“部署说明”。前两项各用一句话总结整个分支的最终改动和自测结果。这三个标签保留给最终的分支级汇报；此前不输出这三个标签或占位，各轮修复汇报按工作流的逐轮汇报要求用自己的措辞正常输出。

根据整个分支的实际改动、配置和部署／迁移入口核实“部署说明”：列出需要的 env 名称、是否必填及默认值；SQL／迁移脚本位置、执行顺序与时机，区分启动时自动迁移和手动操作；以及必要的依赖安装、构建、重启或数据回填步骤。未核实事项标为缺口，仅在核实无需额外操作后写“无需额外部署操作”。

适用栏目保持简短，引用已有证据，不重写各轮报告或已丢弃的发现。
