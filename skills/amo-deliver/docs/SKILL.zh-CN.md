# amo-deliver

## 元数据

- name: `amo-deliver`
- description: 已完成的功能或分支需要最终验收与交付收尾、内部或外部审查意见轮次处理，或交付已审分支时使用。自动推进独立终审与核实后的修复直至收敛。不用于开发中审查、单条意见核实或从需求开始的全程协调。
- version: `0.8.0`

# Amo Deliver

对完成分支执行收尾闭环：本地体验、独立终审、意见轮次与收敛交付。

## 共享输出标记

每阶段汇报首行行内加 `📦 [amo-deliver]` 前缀，不单独成段。

## 使用场景

- 开发已完成，用户要求收尾、验收或交付该功能。
- amo-workflow 进入最终验收与交付收尾。
- 收尾期间收到审查报告，或用户要求推送、移交已审分支。

## 不使用场景

- 开发中的功能审查；使用 amo-review。
- 不涉及收尾的单条意见核实；使用 amo-check。
- 从需求到验收的全程协调；使用 amo-workflow。

## 工作流

1. 从上下文确定分支与验收进度，读取项目规则。请用户本地体验已完成的功能；已有验收结果仍有效时直接复用。需要调整则转 amo-improve 或 amo-fix，之后回到收尾。
2. 自动执行内部终审：
   - 已完成的独立审查仍覆盖目标代码、需求及验收范围时，直接复用；不因交付进入新阶段就再开一次审查。实现者自查不能充当独立审查。相关变化使覆盖失效时，安排审查受影响范围。
   - 默认使用一个审查会话。仅当改动存在两个不同的高风险方向，值得互补审查时，才使用两个，例如业务正确性与并发安全，或迁移完整性与回滚。不能仅因文件数量多就开两个：样式调整、批量组件替换在未引入上述风险时仍使用一个。每轮重新判断；在“轮次状态”中说明数量，使用两个时还须说明各自重点及一个会话不足的原因。
   - 需要新审查时，读取 orchestration skill，按其运行时指南，在 Orca 中启动所选数量的全新 Claude Code 审查会话，沿用已配置模型。向每个会话提供相同的分支、基线与目标版本，任务为只读审查，明确要求读取并使用 `amo-review`。代码审查遵守其规则，Orca 负责会话执行和报告回传。缺少 `amo-review` 时报告能力缺口，不擅自替换其他审查 skill 或安装外部审查 CLI。
   - 每份派工都须包含下述验证约束及已有自测证据：测试版本、命令、覆盖范围、结果与产物位置。审查者按 `amo-review` 独立判断并处理证据。仅在存在针对性检查无法覆盖的具体验证需求时，才运行全量测试。
   - 协调同一本机上各审查会话的补充验证：启动测试或构建前，审查者通过 orchestration 的请求／回复协议提交待验证问题、命令和范围。协调者同一时间只准许一个验证命令运行，也包括自己的检查；测试默认使用一个 worker。获得安排后，审查者可以自行执行检查，其他会话继续读代码。记录所属任务／进程句柄，确保取消能覆盖后台工作。超时后先检查状态与资源占用，有理由才重试，不自动重跑或扩大范围。检查无法完成时，停止其所属命令，收集代码审查结论并明确验证／清理缺口，不无限等待或改称通过。
   - 按 orchestration 完成协议收集本轮所选会话的全部报告；协议要求结束当前轮次时结束，结果全部返回后再处理本轮，不让用户复制报告。所需能力不可用时报告阻碍并保留待办任务，不替换审查者，不声称已完成。
   - 按轮次、严重度、主张和状态登记意见，去重，保留 Critical/High/Medium；Low 静默丢弃。
3. 处理每轮内部或外部意见；外部报告由用户粘贴：
   - 动代码前读取并使用 amo-check。分类为必修、可接受取舍（将剩余影响记入残余风险清单）、误报（静默丢弃）。未核实的主张保留为缺口。继续修复前先检查第 4 步的止损条件。
   - 对必修项指出引入 commit 和修复思路。在已有修复授权内连续推进；仅在需求改变、范围扩大或缺权限时提问。
   - 默认直接在目标分支已有的 worktree 或主工作区中修复，保留无关改动。目标分支尚无检出目录时，直接为该分支创建 worktree。仅在存在冲突的并行修改，或明确隔离要求导致无法使用现有目录时，才额外创建临时 worktree 和修复分支，并说明原因。遵循当前环境的 worktree 管理规则。
   - 每个新增回归测试先证明在修复前代码上因预期原因失败，再证明修复后通过。采用真实生产方数据结构和相关边界场景。执行相关测试及适用的构建／类型检查。
   - 对最终 diff 做三维自审：新机制与既有行为的组合、触发频率、跨轮次或跨日运行后的稳态。更新残余风险，不承诺零缺陷。
   - 仅按授权提交、整合验证通过的修复，确认目标分支已包含预期修复后才能报告修复已交付。确认临时资源中没有未提交或未转移的改动后，在 Git 授权内清理本次创建的临时 worktree 和修复分支；保留目标分支及原有 worktree。整合或清理受阻时保留资源，并说明名称、位置和原因。
   - 未触发止损规则时，在修复后的版本上重复第 2 步。
4. 跟踪轮次和严重度趋势；影响未递减时明说。后续审查确认修复引入新问题时，停止打补丁：使用 amo-draft 写明已知限制，准备独立后续需求。是否带限制交付交由用户决定，不自动合并。经过两轮修复后，主动提醒用户该止损规则。
5. 提供提交链、各轮结果和剩余限制，交用户最终验收。用户明确要求推送时，确认未推送提交并推送分支，报告实际结果。

## 关键规则

- 优先采用解决已确认问题的最小必要修复，不顺带重构无关代码或扩展功能；检查受影响的既有行为，验证修复没有引入新的回归。
- 审查者与交付会话独立；使用两个会话时，彼此也须独立。共享审查目标、必要需求、仓库规则、验证约束及客观自测证据，不传交付讨论、拟定修复或既往审查报告。每次新审查轮次使用全新会话；复用已完成且仍有效的审查不另开轮次。
- 用户报告电脑资源紧张时，先停止本轮审查所属的验证命令，再继续诊断。取消审查时，按运行时的归属与取消协议，同时停止被派工的 agent 及其所属的后台测试／构建进程，保留无关会话和开发服务。确认退出后才能报告已停止；无法核实归属或退出时，说明残留进程与清理缺口，不声称完成。被取消的审查保留为未完成，未经用户指令不重新启动。
- 核实批评，不为维护实现而拒绝意见；未获用户决定时，不把延期风险视为已接受。
- commit 与 push 授权分离。按项目权限提交确认的修复；推送、合并和对外移交需要明确指令。

## 输出

使用用户的语言和要求的详略程度，先回答当前问题。完整交付物按下方格式输出，保留标签顺序并省略不适用的章节。针对局部追问，只回答该问题和理解答案所需的限定，不重复整份报告，也不重新启动工作流路由。

```text
📦 [amo-deliver] 收尾闭环：<分支>
轮次状态：
修复交付：
收敛情况：
交付状态：
```

整个 amo-deliver 完成后的最后一次回复，在“交付状态”后依次追加“修改说明”“自测结果”“部署说明”。前两项各用一句话总结整个分支的最终改动和自测结果；此前不输出这三个标签，也不留占位。

根据整个分支的实际改动、配置和部署／迁移入口核实“部署说明”：列出需要的 env 名称、是否必填及默认值；SQL／迁移脚本位置、执行顺序与时机，区分启动时自动迁移和手动操作；以及必要的依赖安装、构建、重启或数据回填步骤。未核实事项标为缺口，仅在核实无需额外操作后写“无需额外部署操作”。
