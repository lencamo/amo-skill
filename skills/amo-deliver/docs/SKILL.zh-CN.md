# amo-deliver

## 元数据

- name: `amo-deliver`
- description: 已完成的功能或分支需要最终验收与交付收尾、内部或外部审查意见轮次处理，或交付已审分支时使用。自动推进独立终审与核实后的修复直至收敛。不用于开发中审查、单条意见核实或从需求开始的全程协调。
- version: `0.10.0`

# Amo Deliver

对完成分支执行收尾闭环：本地体验、独立终审、意见轮次与收敛交付。

## 共享输出标记

每阶段汇报首行行内加 `📦 [amo-deliver]` 前缀，不单独成段。

## 使用场景

- 开发已完成，用户要求收尾、验收或交付该功能。
- amo-workflow 进入最终验收与交付收尾。
- 收尾期间收到审查报告，或用户要求推送、移交已审分支。

## 不使用场景

- 开发中的功能审查；使用 amo-review。
- 不涉及收尾的单条意见核实；使用 amo-check。
- 从需求到验收的全程协调；使用 amo-workflow。

## 工作流

1. 从上下文确定分支与验收进度，读取项目规则。请用户本地体验已完成的功能；已有验收结果仍有效时直接复用。需要调整则转 amo-improve 或 amo-fix，之后回到收尾。
2. 按风险安排独立审查：
   - 已完成的独立审查仍覆盖目标代码、需求及验收范围时，直接复用；不因交付进入新阶段就再开一次审查。实现者自查不能充当独立审查。相关变化使覆盖失效时，安排审查受影响范围。
   - 启动会话前应用 amo-review 的风险标准。仅包含展示文字、注释或非执行性文档且行为不变时，复用实施自检，将独立审查记为不适用；用户明确要求或项目规则要求时除外。不得将可执行指令、选择器、协议值或业务规则当作无害文档。其他改动使用一个独立会话。
   - 按实际风险自动选择本地 `/code-review` 力度：范围明确的低风险修改用 `low`，常规功能用 `medium`，敏感或复杂行为用 `high`；仅有具体深入分析需要时用 `max`。简短说明力度及原因。遵守用户明确指定的力度，不依次跑各档、不继承上次档位，也不只因文件多就升级。
   - 读取 orchestration skill，按运行时指南，在 Orca 中启动全新 Claude Code 会话，沿用已配置模型。使用内置本地 `/code-review`，不使用旧 GitHub 插件、云端 Code Review、ultrareview 或 OCR delegate。显式传入力度及解析后的审查目标；连续已提交范围使用 `/code-review <effort> <base-sha>..<target-sha>`，其中基线已解析到适当共同祖先。保留用户明确选择的提交。包含工作区改动时，明确已暂存、未暂存及未跟踪内容，检测审查期间这些输入是否变化，不静默遗漏或替换范围。
   - 仅提供固定范围、简短需求及相关项目约束、已有验证证据（版本、命令、范围、结果及可用日志）。要求只读报告具体缺陷和实质缺口，不加 `--fix`、`--comment`，不运行测试或构建；运行时证据不足时指出另行验证所需的针对性检查。不在内置审查之外再派一轮 amo-review。本地命令、显式力度或所需范围不可用时，报告能力缺口，不替换审查者或安装工具。
   - 按 orchestration 完成协议收回实际结论；协议要求结束轮次时结束。后台 `/code-review` 的启动消息或任务句柄不等于审查报告，worker 必须等实际结果返回后再报完成。自动处理返回结果，不让用户复制报告。不可用或中断的覆盖记为未完成，不改称通过。
   - 每次审查尝试结束后，保留可用的结论／输出，核对已登记的测试／构建句柄，按对应运行时的取消协议停止残留的所属验证命令。确认退出后才能报告进程清理完成。按 orchestration 当前指南，自动或显式释放归属已确认的专用终端；已安排或等待释放不等于已释放。尊重保留开启和用户接管，保留原有终端，以及承载仍需使用的开发／验收服务的终端。终端释放、临时工作区清理和日志保留分别处理；符合条件的终端释放不以删除工作区或日志为前提。
   - 按轮次、严重度、主张和状态登记意见，去重，保留 Critical/High/Medium；Low 静默丢弃。
3. 处理每轮内部或外部意见；外部报告由用户粘贴：
   - 动代码前读取并使用 amo-check。分类为必修、可接受取舍（将剩余影响记入残余风险清单）、误报（静默丢弃）。未核实的主张保留为缺口。继续修复前先检查第 4 步的止损条件。
   - 对必修项指出引入 commit 和修复思路。在已有修复授权内连续推进；仅在需求改变、范围扩大或缺权限时提问。
   - 默认直接在目标分支已有的 worktree 或主工作区中修复，保留无关改动。目标分支尚无检出目录时，直接为该分支创建 worktree。仅在存在冲突的并行修改，或明确隔离要求导致无法使用现有目录时，才额外创建临时 worktree 和修复分支，并说明原因。遵循当前环境的 worktree 管理规则。
   - 行为修复在有帮助时增加针对性回归测试，证明修复前因预期原因失败、修复后通过。采用真实生产方数据结构和相关边界场景，遵守 amo-implement 的适度验证规则；简单文字修正无需新增回归测试组。测试／构建留在本验证步骤执行，保留实际结果。
   - 对照受影响的既有行为自查修复；涉及触发频率、重复运行或跨日状态时再检查对应影响。更新残余风险，不承诺零缺陷。
   - 仅按授权提交、整合验证通过的修复，确认目标分支已包含预期修复后才能报告修复已交付。确认临时资源中没有未提交或未转移的改动后，在 Git 授权内清理本次创建的临时 worktree 和修复分支；保留目标分支及原有 worktree。整合或清理受阻时保留资源，并说明名称、位置和原因。
   - 未触发止损规则时，在修复版本上复核修复差异及受影响契约，保留未变代码的有效覆盖。仅对修复使覆盖失效的部分安排独立复审；只有新行为或风险使更广覆盖失效时，才扩大到整个分支。
4. 跟踪轮次和严重度趋势；影响未递减时明说。后续审查确认修复引入新问题时，停止打补丁：使用 amo-draft 写明已知限制，准备独立后续需求。是否带限制交付交由用户决定，不自动合并。经过两轮修复后，主动提醒用户该止损规则。
5. 提供提交链、各轮结果和剩余限制，交用户最终验收。用户明确要求推送时，确认未推送提交并推送分支，报告实际结果。

## 关键规则

- 优先采用解决已确认问题的最小必要修复，不顺带重构无关代码或扩展功能；检查受影响的既有行为，验证修复没有引入新的回归。
- 审查者与交付会话独立。共享审查目标、必要需求、仓库规则、验证约束及客观自测证据，不传交付讨论或预期结论。针对修复的复核可提供已确认的触发条件及所需行为，不回放整份旧报告。新的独立审查使用全新会话；复用有效证据不另开轮次。
- 耗时只作为效率信号，不是固定截止时间或质量结论。审查异常拖长时，通过运行时支持的方式查看进度、范围、资源占用及意外测试／构建工作。针对原因纠正，不自动重跑、扩大范围或提高力度；报告停滞或剩余缺口，不无声等待。运行时故障超时与审查质量分开处理。
- 用户报告电脑资源紧张时，先停止本轮审查所属的验证命令，再继续诊断。取消审查时，按运行时的归属与取消协议，同时停止被派工的 agent 及其所属的后台测试／构建进程，保留无关会话和开发服务。确认退出后才能报告已停止；无法核实归属或退出时，说明残留进程与清理缺口，不声称完成。被取消的审查保留为未完成，未经用户指令不重新启动。
- 审查／验证结果与清理状态分开记录。释放失败不会使已完成审查失效，也不是另开审查会话的理由。仅针对失败的清理遵循运行时恢复指引，记录保留资源、原因及下一步。worker 尝试失败时，确认前一次尝试已停止后，按运行时的同任务重试协议处理；遵守重试限制，不新建任务绕过。
- 核实批评，不为维护实现而拒绝意见；未获用户决定时，不把延期风险视为已接受。
- commit 与 push 授权分离。按项目权限提交确认的修复；推送、合并和对外移交需要明确指令。

## 输出

使用用户的语言和要求的详略程度，先回答当前问题。完整交付物按下方格式输出，保留标签顺序并省略不适用的章节。针对局部追问，只回答该问题和理解答案所需的限定，不重复整份报告，也不重新启动工作流路由。

```text
📦 [amo-deliver] 收尾闭环：<分支>
轮次状态：
修复交付：
收敛情况：
交付状态：
```

整个 amo-deliver 完成后的最后一次回复，在“交付状态”后依次追加“修改说明”“自测结果”“部署说明”。前两项各用一句话总结整个分支的最终改动和自测结果；此前不输出这三个标签，也不留占位。

根据整个分支的实际改动、配置和部署／迁移入口核实“部署说明”：列出需要的 env 名称、是否必填及默认值；SQL／迁移脚本位置、执行顺序与时机，区分启动时自动迁移和手动操作；以及必要的依赖安装、构建、重启或数据回填步骤。未核实事项标为缺口，仅在核实无需额外操作后写“无需额外部署操作”。
