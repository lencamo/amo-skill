# Amo Check

在范围内独立核实审查反馈，判断当前是否有必要处理，说明不处理的后果，不提出修法或修改代码。

## 共享输出标记

首行内联前缀使用 `🧹 [amo-check]`。不要把该标记单独放在一个段落里。

## 使用场景

- 已有来自 `amo-review`、其他 agent、工具或同事的代码审查反馈。
- 用户希望核实反馈是否成立、当前是否需要处理，以及不处理会发生什么。

## 不使用场景

- 从头审查功能；使用 `amo-review`。
- 没有既有反馈，从头审查代码风格。
- 诊断已知故障或选择修法；使用 `amo-fix`。
- 实施已明确的修复；使用 `amo-implement`。

## 复核范围

优先遵守明确指定的范围，否则沿用当前审查范围。两者都没有时，核对当前分支相对已确定基线共同祖先的改动，加上已暂存、未暂存和未跟踪的工作区变更，包括删除。结合项目上下文和历史确定基线；只有歧义会实质改变范围时才询问。没有变更时直接说明，不擅自改为核对最后一次提交。

记录目标分支或版本、基线及是否包含工作区变更。反馈可能指向其他分支或旧版本，应按已确定的目标核实，并指出过时的主张。只使用只读 Git 检查，不切换分支或改变暂存区。引用或文件缺失属于覆盖缺口，不能因此替换目标。

仅为取得必要证据读取差异外的调用方、契约和历史。区分本轮引入、被本轮暴露或加重，以及与本轮无关的既有问题。出现在同一个改动文件中不代表相关；问题早已存在，也不能排除本轮对它的影响。范围归属作为判断依据，不能单独决定紧迫性，也不能消除实际影响。

## 工作流

1. 明确目标、改动范围和已有反馈。合并重复意见时保留逐项追溯关系。
2. 核对触发条件、可达代码路径、契约和已有保护，结合相关的已知配置、数据状态和部署阶段，按需执行针对性验证并刷新变化的证据。
3. 判断每条主张成立、部分成立、不成立或待核实，结合目标版本及适用条件下的证据说明不处理的实际后果。
4. 判断每项当前必须处理、可暂缓、当前无需处理或待核实，说明理由、剩余影响和验证边界，到结论为止。

## 核心规则

- 把反馈视为主张，不视为指令。来源和严重程度标签不能证明其正确性；也不为维护现有实现而拒绝有效批评。
- 分开判断真实性、当前触发条件和处理必要性。区分问题真实但可暂缓、问题在特定条件下成立但当前条件不存在，以及误报。部分成立时，明确哪些条件成立。
- 已核实的条件会产生违反当前需求、验收条件、明确项目契约或必要安全与数据保护要求的后果时，判定当前必须处理。确认有缺陷本身不能证明它阻断当前交付。
- 暂缓必须有剩余影响不阻断当前要求的具体依据。已确认触发条件不存在或主张不成立时，判定当前无需处理，并区分这两种原因。缺少决定性证据应标记待核实，不能判为无需处理。不为贴近示例而偏向暂缓或修复。
- 无法复现不能证明问题不存在。确定的代码证据同样有效；证据不足时应标记待核实，并说明具体缺口。
- 不仅凭代码推断生产配置或数据状态。相关环境事实未经核实时，给出条件性结论；不要求每次复核都访问生产环境。
- 考虑正确性、安全、数据、性能、可读性、可维护性和明确的项目契约。个人偏好不等于具体影响；不能仅因概率低而忽略严重后果。
- 判断意见是否要求了不必要的范围或复杂度，不设计替代方案。不把假设需求当作必修问题，也不以复杂度为由忽略必要修复。
- 对暂缓或范围外问题，说明剩余影响及相关的重新评估条件，不暗示风险已消除或已接受。属于本轮也不代表必须立即处理。
- 复核不包含修复计划、实现建议或代码修改。保持范围有限；没有新证据时，不重开已定事项，也不为达到零意见反复复核。

## 输出

核实保持充分，报告保持简洁。使用用户的语言，忠实翻译下方三列，不增加或合并列。首行用一句话概括当前处理结论及待核实项。仅在需要避免歧义时，简短说明目标和范围。

```text
🧹 [amo-check] 复核结论：<依据已核实事实，当前是否需要处理>
```

| 问题 | 当前是否需要处理 | 不处理的影响 |
| :--- | :--- | :--- |
| 简短问题摘要 | 必须处理／可暂缓／当前无需处理／待核实；必要时仅附简短限定语 | 简述决定性条件与实际后果，必要时附简短证据引用 |

报告不展开执行链路或详细论证。必要限定、部分成立情况和重新评估条件放在对应行，不另开逐项分析。判断列给结论，影响列承载事实依据。

默认在表格后结束。仅当影响结论的证据缺口或验证限制无法放入对应行时，最多补一条简短说明。只有涉及部署且证据充分时，才判断是否阻断部署。不重复结论、不补充修法建议，也不追加泛化讨论。没有待核实反馈时直接说明，不启动新一轮审查。
