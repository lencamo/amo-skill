# amo-detail

## 元数据

- name: `amo-detail`
- description: 当用户希望将已讨论的方案展开，了解 Agent 准备如何实施，以及实施后的流程、前端行为、后端处理和数据会如何变化时使用。不用于初始方案设计、挑战既定方案、编码或代码审查。
- version: `0.4.0`

# Amo Detail

将已讨论的方案展开为具体实施安排和实施后的行为。方案是主要依据，代码是按需使用的辅助证据。

## 共享输出标记

首行内联前缀使用 `🔎 [amo-detail]`。不要把该标记单独放在一个段落里。

## 使用场景

- 已有方案，由用户提供，或通过 `amo-feature`、`amo-improve`、`amo-fix`、`amo-refactor` 或 `amo-best` 形成。
- 用户希望了解 Agent 准备如何落实方案，以及实施后会发生什么变化。
- 用户希望了解具体流程、前端、后端、存储或定时任务细节，而不只是方案概述。

## 不使用场景

- 尚未确定方案方向；使用 `amo-feature`、`amo-improve`、`amo-fix` 或 `amo-refactor`。
- 用户希望挑战已有方案；使用 `amo-best`。
- 用户要求编码实施或审查已实现代码。

## 工作流

1. 从讨论中明确方案、目标、范围和已确定的决策。
2. 串联实施后从用户操作或系统触发到结果的完整流程，说明影响的功能和模块。
3. 展开前端实现：页面变化、复用或调整哪些现有组件和接口及其方式、数据来源、状态归属、请求处理，以及实施后的显示、交互和状态流转。
4. 展开后端实现：入口与输入、复用或调整哪些现有处理逻辑及其方式、业务规则、数据读写、存储变化（表和字段）、结果及使用方；涉及定时任务时说明触发方式或执行时间、处理和结果。
5. 核对前端请求、后端输入、响应与界面更新的衔接，列出影响实施的待决事项。
6. 说明常规部署之外的操作（定时任务、数据回填、表迁移等）、作用对象和必要时机或依赖；无额外操作时注明，不确定项列入待决事项。

## 核心规则

- 以讨论方案为主，沿用已有决策；代码仅按需核实。
- 每项主要变化讲清“做什么、怎样实现、实施后怎样运作”，不用概述或名称清单代替。
- 区分已确定的决策、拟实施细节和待决问题；不编造现状，不把常规实施细节都留待用户确认。
- 只展开方案范围，不擅自增加功能、改变状态或引入架构；不涉及的部分直接说明。
- 只解释、不实施；部署之外的执行顺序和验证计划按用户要求补充。

## 输出

输出标签和内容使用用户的语言。

```text
🔎 [amo-detail] 场景：方案实施详情
方案：
整体链路：
前端实施：
后端实施：
影响范围：
部署事项：
待决事项：
```
