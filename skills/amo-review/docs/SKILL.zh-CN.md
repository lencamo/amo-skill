# amo-review

## 元数据

- name: `amo-review`
- description: 对工作区变更、指定提交或功能分支中的已实现功能，按风险进行静态审查，查找需求遗漏、逻辑错误和 Bug。用户要求检查实现是否正确或能否合并时使用。不用于纯代码风格审查、方案设计，或针对已知异常选择修复方案。
- version: `0.6.0`

# Amo Review

基于具体证据，按改动风险投入适当深度审查功能正确性。单独调用时执行审查；交付流程中提供标准，不重复 amo-deliver 安排的独立审查。默认静态分析并报告，不修改代码。

## 共享输出标记

完整交付物的首行内联前缀使用 `🔍 [amo-review]`。不要把该标记单独放在一个段落里。

## 使用场景

- 用户希望对照需求检查已实现行为，或查找逻辑错误、遗漏场景与潜在 Bug。
- 审查目标是工作区变更、指定提交、提交范围或功能分支。

## 不使用场景

- 仅审查代码风格、冗余、抽象或类型表达。
- 核实已有审查反馈及当前是否需要处理；使用 `amo-check`。
- 分析已知异常的根因并选择修复方案；使用 `amo-fix`。
- 实施前设计或复核方案。

## 审查范围

优先遵守用户明确指定的范围。用户泛化要求审查实现时，在功能分支上默认审查整个分支，在基线分支上默认审查工作区。两者均无变更时直接说明，不擅自改为审查最后一次提交。结合项目上下文和历史确定不明确的基线；只有歧义会实质改变范围时才询问。

| 范围 | 审查内容 |
| :--- | :--- |
| 工作区 | 相对 `HEAD` 的已暂存与未暂存跟踪文件合并差异，加上未跟踪文件全文；同时检查删除和新增内容。 |
| 指定提交 | 各指定提交的改动，或用户明确指定提交范围的净差异。保留用户明确选择的提交，不将中间其他提交一并纳入。 |
| 功能分支 | 将基线和目标解析为提交 ID，确定共同祖先，审查从该分叉点到目标的净差异。历史用于解释意图，不把最终状态已经修复的中间问题重新报出。 |

一次性记录审查模式、基线、目标及是否包含未提交变更。读取被审查版本的文件；工作区文件可能与指定提交或分支不同。保留明确排除的范围，将实质未读或不可用的部分记录为缺口，不计为已审。

只使用只读 Git 检查，保留工作区和暂存区。引用缺失或文件不可读属于覆盖缺口，不能因此擅自替换审查范围。

## 审查深度

- 按行为及出错后果分级，不按文件数或差异大小判断。纯展示文字、注释和非执行性文档只需检查替换、遗漏及意外改动。选择器、协议、模板或业务判断使用的文字，以及可执行指令，可能改变行为，须按对应风险审查。
- 局部改动检查变化的逻辑及直接影响的契约；常规功能追踪变化的输入、状态和输出；权限、资金、数据完整性、迁移或并发即使只改少量代码，也须追踪相关保护和失败路径。
- 只选择下方适用维度。仅在变化的行为或具体疑点需要时，查阅[技术栈检查](references/stack-checks.zh-CN.md)的相关内容；不为每次改动展开全部检查或全仓审计。

## 工作流

1. 明确范围、预期行为和适用项目规则。复用共享上下文，区分需求与推断，检查遗漏、行为偏离及无关改动。
2. 分批读取范围内的差异。重复替换合并检查并核对覆盖；仅为理解变化的行为或解决具体疑点读取调用方、依赖、历史及配置。既检查新增，也检查被删除的行为。
3. 根据可达输入、已有保护及可观察后果核实候选缺陷。确定性代码证据已足够，不要求每条发现都运行复现。排除缺乏依据的候选项，将影响结论的不确定性保留为缺口。
4. 相关代码、测试、配置和环境未变时，复用已有验证证据；只改提交信息不会使证据失效。审查默认不运行测试或构建。具体疑点需要运行时证据时，指出另行验证所需的针对性检查。遵守用户或项目明确要求的验证，不擅自扩大范围；区分静态判断、复用结果及缺失证据。
5. 报告已确认问题、实际审查范围及实质排除项或缺口。目标变化时刷新受影响证据。范围内检查及候选问题处理完即结束；没有发现也是有效结果。不为寻找更多意见或凑时长重开未变化的范围。

## 检查维度

| 维度 | 检查内容 |
| :--- | :--- |
| 需求与逻辑 | 行为遗漏、错误结果、边界输入、异常路径及不完整修复。 |
| 接口与状态 | 调用方失效、契约不匹配、非法状态转换和持久化不一致。 |
| 安全与数据 | 权限绕过、不安全输入、敏感数据泄露、数据丢失和错误写入。 |
| 并发与规模 | 竞态、重复执行、共享状态错误和预期负载下的失败。 |
| 性能 | 足以影响所需行为或使用体验的性能退化。 |
| 测试与验证 | 关键逻辑是否被覆盖，检查是否能暴露其失败。缺少测试本身属于验证缺口，不能直接证明存在 Bug。 |

## 核心规则

- 只报告影响审查范围内行为的具体缺陷。明确触发条件、代码路径、错误结果与影响，以及现有保护为什么无法阻止；区分回归和既有缺陷。
- 报告前重新读取相关代码行和调用方。引用被审查版本的精确文件与行号，给出复现方式或代码证据，以及足够解决问题的最小修复建议。
- 不把猜测、明确取舍、风格偏好或无关清理当作问题。风格问题导致具体行为缺陷时，可以报告该缺陷。
- 简短说明范围，按实际影响将缺陷分为 Critical、High、Medium 或 Low，省略空栏目。缺少测试及其他未验证项归入验证部分。
- 没有发现问题也是有效结果。没有已核实缺陷时，简洁给出无发现结论、审查范围，以及相关验证结果或覆盖缺口。不凑问题，也不宣称已经排除所有 Bug。
- 审查请求不代表授权修复。用户明确要求修复时，保持在授权范围内，审查修复后的差异，并在最终结论前重新完成相关验证。

## 输出

使用用户的语言和要求的详略程度，先回答当前问题。完整交付物按下方格式输出，保留标签顺序并省略不适用的章节。针对局部追问，只回答该问题和理解答案所需的限定，不重复整份报告，也不重新启动工作流路由。
