# amo-review

## 元数据

- name: `amo-review`
- description: 审查工作区变更、指定提交或整个功能分支中的已实现功能，查找需求遗漏、逻辑错误和 Bug。用户要求检查实现是否正确或能否合并时使用。不用于纯代码风格审查、方案设计，或针对已知异常选择修复方案。
- version: `0.4.0`

# Amo Review

基于具体证据审查功能正确性，默认只报告问题，不修改代码。

## 共享输出标记

完整交付物的首行内联前缀使用 `🔍 [amo-review]`。不要把该标记单独放在一个段落里。

## 使用场景

- 用户希望对照需求检查已实现行为，或查找逻辑错误、遗漏场景与潜在 Bug。
- 审查目标是工作区变更、指定提交、提交范围或功能分支。

## 不使用场景

- 仅审查代码风格、冗余、抽象或类型表达。
- 核实已有审查反馈及当前是否需要处理；使用 `amo-check`。
- 分析已知异常的根因并选择修复方案；使用 `amo-fix`。
- 实施前设计或复核方案。

## 审查范围

优先遵守用户明确指定的范围。用户泛化要求审查实现时，在功能分支上默认审查整个分支，在基线分支上默认审查工作区。两者均无变更时直接说明，不擅自改为审查最后一次提交。结合项目上下文和历史确定不明确的基线；只有歧义会实质改变范围时才询问。

| 范围 | 审查内容 |
| :--- | :--- |
| 工作区 | 相对 `HEAD` 的已暂存与未暂存跟踪文件合并差异，加上未跟踪文件全文；同时检查删除和新增内容。 |
| 指定提交 | 各指定提交的改动，或用户明确指定提交范围的净差异。保留用户明确选择的提交，不将中间其他提交一并纳入。 |
| 功能分支 | 将基线和目标解析为提交 ID，确定共同祖先，审查从该分叉点到目标的净差异。历史用于解释意图，不把最终状态已经修复的中间问题重新报出。 |

审查前记录模式、基线、目标和文件清单。读取被审查版本的文件；工作区文件可能与指定提交或分支不同。审查提交或分支时说明是否包含未提交变更，用户未要求时将其排除在范围之外。

只使用只读 Git 检查，保留工作区和暂存区。引用缺失或文件不可读属于覆盖缺口，不能因此擅自替换审查范围。

## 工作流

1. 明确范围，从用户请求、需求、验收条件、项目文档、测试和已有契约确认预期行为。直接读取适用的仓库规则及目录专属规则；必须使用的规则来源不可读或其格式无法处理时，记录为覆盖缺口。区分明确意图和推断。对照既定目标检查改动，识别需求遗漏、行为偏离和无关改动；范围偏离与功能缺陷分开说明。
2. 完整读取选定差异及相关上下文：调用方、被调用代码、删除前内容、测试、配置和存储契约。追踪输入、处理、状态变化、持久化与输出。结果来源或记录生命周期变化时，检查新可达状态下结果上的原有操作，包括记录已不在原来源中的情况。
3. 按下列维度，结合真实契约和预期负载检查。对高风险的变更流程，明确操作前后必须保持成立的条件，再通过改变时序、输入格式或权限范围，选择相关的对抗场景。例如旧响应覆盖新状态、刷新中断活动会话、复用组件保留过期状态。签名、返回值或行为变化时追踪受影响的调用点。针对 Bug 修复，检查直接关联路径是否存在相同缺陷，确认修复覆盖所有受影响入口。不扩展成无关的全仓审计，也不修复未经要求的部分。
4. 根据可达输入、下游行为和现有保护核实候选问题。对于依赖时序、状态或运行环境的行为，优先构造最小且可观察的复现；确定性的静态证据同样有效。检查已有验证证据及覆盖范围。相关代码、测试、配置和环境未变时复用结果；仅修改提交信息不会使证据失效。针对具体疑点或覆盖缺口补充检查，遵守调用方的验证约束。使用执行一次即退出的命令，确认测试工具实际采用了指定文件范围及并发设置，保留真实退出状态和完整失败输出。区分实际执行的检查、复用结果、静态推断和无法执行的检查。审查结论依赖真实依赖的特定行为，而 Mock 或替代服务未覆盖该行为时，应说明验证缺口。
5. 对每个范围内文件记录已审查，或说明跳过原因。报告前若目标或相关工作区文件变化，刷新受影响的证据。受委派的审查报告须标明基线和目标、汇总已审／跳过的文件覆盖，并区分已执行、复用和无法执行的检查，供协调者判断完成情况。

## 检查维度

| 维度 | 检查内容 |
| :--- | :--- |
| 需求与逻辑 | 行为遗漏、错误结果、边界输入、异常路径及不完整修复。 |
| 接口与状态 | 调用方失效、契约不匹配、非法状态转换和持久化不一致。 |
| 安全与数据 | 权限绕过、不安全输入、敏感数据泄露、数据丢失和错误写入。 |
| 并发与规模 | 竞态、重复执行、共享状态错误和预期负载下的失败。 |
| 性能 | 足以影响所需行为或使用体验的性能退化。 |
| 测试与验证 | 关键逻辑是否被覆盖，检查是否能暴露其失败。缺少测试本身属于验证缺口，不能直接证明存在 Bug。 |

## 核心规则

- 只报告影响审查范围内行为的具体缺陷。明确触发条件、代码路径、错误结果与影响，以及现有保护为什么无法阻止；区分回归和既有缺陷。
- 报告前重新读取相关代码行和调用方。引用被审查版本的精确文件与行号，给出复现方式或代码证据，以及足够解决问题的最小修复建议。
- 不把猜测、明确取舍、风格偏好或无关清理当作问题。风格问题导致具体行为缺陷时，可以报告该缺陷。
- 简短说明范围，按实际影响将缺陷分为 Critical、High、Medium 或 Low，省略空栏目。缺少测试及其他未验证项归入验证部分。
- 没有发现问题也是有效结果。没有已核实缺陷时，简洁给出无发现结论、审查范围，以及相关验证结果或覆盖缺口。不凑问题，也不宣称已经排除所有 Bug。
- 审查请求不代表授权修复。用户明确要求修复时，保持在授权范围内，审查修复后的差异，并在最终结论前重新完成相关验证。

## 输出

使用用户的语言和要求的详略程度，先回答当前问题。完整交付物按下方格式输出，保留标签顺序并省略不适用的章节。针对局部追问，只回答该问题和理解答案所需的限定，不重复整份报告，也不重新启动工作流路由。
